# Instructions for coding agents

These instructions apply to any automated agent (Claude Code, Codex, Cursor, Copilot agents, or similar) working in this repository. Read them before running or editing anything. Human contributors should follow them too.

## What this repository is

The public record of one paper: *Heat-Kernel Cryptanalysis of SHA-256: A Geometric Study of State Evolution* (Bee Rosa Davis, 2026). Its value is that every number in the manuscript is traceable to a frozen receipt and an independent verifier, and that the December 2025 claims it replaced are preserved alongside the audit that withdrew them. Your job, whatever the task, is to keep that chain intact. `README.md` describes the layout; `REVIEWER_GUIDE.md` describes how the chain is checked.

## Invariants

1. **Receipts are immutable.** Never edit, regenerate, delete, or "fix" anything under `publication/evidence/`. Every runner refuses to overwrite an existing receipt directory. A new measurement goes into a new directory, with its protocol saved before execution, and becomes a new receipt with its own verifier checks.

2. **Hash-locked sources.** The receipts record SHA-256 hashes of the code that produced them, and `publication/verify_evidence.py` checks those hashes against the files as stored. Do not edit these files:
   - `publication/repro_source/**` (byte-exact snapshot of the primary run)
   - `analysis/publication_study.py`, `analysis/publication_followup.py`, `analysis/publication_matched.py`
   - `src/sha256/core.py`, `src/sha256/batch.py`
   - `publication/evidence/followup/search.npz`, `publication/evidence/followup/cubes.npz` (inputs to the matched family)
   If a measured function must change, that is a new experiment: new runner, new receipt directory, new checks, and a manuscript change that reports both the old and the new result.

3. **Byte-exact storage.** `.gitattributes` sets `* -text`. Do not remove it, do not add line-ending conversions, and do not let an editor or formatter rewrite line endings in any tracked file. Never run a formatter across the repository.

4. **Numbers flow one way.** Receipt → `publication/build_paper.py` and `publication/followup_tables.py` → macro files (`numbers.tex`, `followup_numbers.tex`, `*_table.tex`) → `publication/sha256_measurement.tex`. Never type a number into the manuscript, `RESULTS.md`, or `README.md` by hand. Add or change a macro in the table script and cite the macro. `RESULTS.md` is regenerated by `make_release.py`; `README.md` is maintained by hand and must not contain numbers that are not also in a receipt.

5. **Frozen snapshots.** `review/pre_correction_snapshot/`, `review/measurement_edition_snapshot/`, and `review/pre_followup_snapshot/` are historical records. Do not modify them. If a change is ever unavoidable, record the original hashes in a note beside the manifest, as `review/pre_correction_snapshot/MANIFEST_NOTE.md` does.

6. **Verification before any claim.** Before saying that something works, passes, reproduces, or is unchanged, run and read the output of:
   ```
   python -m pytest tests -q                 # expect 46 passed
   python publication/verify_evidence.py     # expect passed: true, 20 checks
   ```
   After changing anything that feeds the manuscript:
   ```
   python publication/build_paper.py
   python publication/make_release.py
   ```
   and inspect `publication/release/package_validation.json`, which must be regenerated from clean extractions of both archives (see the `standalone_arxiv_source` and `extracted_archive_*` fields). Report failures verbatim. Never edit a test or a verifier check to make it pass.

7. **Commit hygiene.** Commit messages are plain descriptions of what changed and why. Do not add automated co-author trailers, tool attributions, or generated boilerplate. The author of record is the repository owner. Never force-push over history you did not create in the same session, and never commit `output/`, `.venv/`, or anything matched by `.gitignore`.

## Claims discipline

The paper's stance is that a measurement is reported as what it is, with its resampling unit, its control family, and its limits. Keep it that way. In particular:

- **No attack claims.** Nothing here establishes a collision, preimage, or distinguishing attack on SHA-256, or a security proof. Published collision attacks reach 37 steps and preimage attacks 45 steps; this work measures working-state responses within the first rounds after a variable enters and does not compete with them. Do not reintroduce language about "breaks," "vulnerabilities," "security horizons," or "attack extensions." That language is exactly what the audit removed.

- **Entry timing.** A variable in message word W_j first affects the state at completed round j + 1, and trailing registers are exact delayed copies of leading ones (`b_r = a_{r-1}`, `c_r = a_{r-2}`, `d_r = a_{r-3}`; likewise for `e`). A zero cube sum in a trailing register before or shortly after entry is transport, not algebraic weakness. Always report rounds since entry alongside total rounds.

- **Bit significance.** Early one-bit and cube responses depend strongly on the significance of the flipped position, because carries propagate upward. Any comparison of a candidate position set against controls must use controls matched on significance (see `analysis/publication_matched.py`), and must report both the paired interval against the control mean and the candidate's rank among control sets, with bootstrap bounds on the rank; the rank is descriptive, not an uncertainty interval. This is how the candidate set's early advantage over uniform controls was shown to be largely a property of high bits; its residual round-2 cube contrast against the matched mean is reported as unresolved, not dismissed.

- **Reference probabilities.** A "one half" reference for a cube zero rate does not establish candidate specificity at early rounds, where the average control rate is itself far from one half and individual sets range widely. Report the control range, and never use a candidate-versus-one-half adjustment to dismiss a candidate-versus-control interval; they test different hypotheses.

- **Saturated regime.** The whole state saturates about six rounds after a variable enters. Tests placed at rounds where every position has saturated (the original round-24 selection, cubes at rounds 8 to 24) are controls, and their null results must be described as expected by construction, not as discoveries.

- **Descriptive intervals stay descriptive.** Bootstrap intervals here are unadjusted and conditional on sampled control sets. Do not upgrade an interval that excludes zero into a claim of an effect without a replication on fresh seeds, and do not delete a replication that failed. Report both.

- **Negative results are results.** Do not remove, soften, or bury a null. Do not add a positive-sounding sentence to an abstract unless a receipt and a matched control support it.

## Adding an experiment

Follow the pattern of `analysis/publication_matched.py`:

1. Define `PROTOCOL` as a literal dict with seeds, sizes, rounds, control pools, statistics and the reason the experiment exists. Save it before computing.
2. Write `environment.json` with Python and NumPy versions and the SHA-256 of every source file the runner imports for measurement, plus any input receipts it reads.
3. Save raw arrays (`.npz`) and summaries (`.json`) with per-unit values, not only means. Bases or whole dataset pairs are the resampling unit; interventions sharing a base are not independent.
4. Extend `publication/verify_evidence.py` with checks that recompute every summary from the arrays and assert the source hashes. Extend `tests/` with construction checks that do not read evidence.
5. Extend `publication/followup_tables.py` (or `build_paper.py`) to emit macros and rows; reference them from the manuscript; update `RESULTS.md` through `make_release.py`.
6. Run tests, verifier, build, release, and regenerate `package_validation.json` from clean extractions. Only then describe the result, and describe it with its limits.
